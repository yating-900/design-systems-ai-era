## 08 从 Braun 到 Apple，好的设计在延续

从实体计算器，到早期 iPhone，再到后期的界面，技术和外观一直在变化。实体按键变成屏幕上的按键，模拟真实按键的阴影和质感，后来也被简化了。Jony Ive 在采访中明确谈到，早期 iPhone 计算器在图形外观和布局上向 Braun 致意。值得继续看的是：变化之中，有哪些帮助人理解和使用的思考被保留下来了？数字仍然需要有规律地排列，不同功能需要被区分，重要操作也需要容易辨认。具体位置和功能有所调整，延续的并不是每一个外形细节。下一页，我们就把 Braun 计算器放大，看三处具体的设计选择，以及它们怎样帮助使用。

## 09 分组、排列与强调，让功能更容易辨认

先不急着读原则，看看照片里具体做了什么。第一，记忆功能的按键集中在上方，形成一个可以辨认的区域。相关功能放在一起，我们就多了一条寻找和理解的线索。第二，主要数字按规律排列成网格，数字之间的位置关系是稳定的，不需要把每个按键都当作一个孤立的符号去找。第三，等号使用了醒目的黄色，与周围按键区分开，帮助我们辨认计算结果的操作。这里的重点不是规定所有产品都用绿色或黄色，而是让分组、位置和颜色承担清楚的作用。再回看上一页的 iPhone：外观变化了，但功能分组、数字排列和视觉强调，仍然是界面需要处理的事情。我们可以由此理解，为什么易懂和对细节的认真处理会成为好设计的品质。沿着这些具体观察，再来看 Rams 总结的十项原则，就有了可以联系的对象。

## 10 迪特·拉姆斯：好设计的十项原则

从刚才的计算器出发，我们已经能观察分组、位置和颜色；但判断好设计，还可以看得更完整。Dieter Rams 把长期设计实践中的思考总结为十项原则。这页保留十项原则的顺序，为了方便理解，我们把它们放成三组。先看用途与感受：创新、实用、美观，关心产品能否借助技术服务真实用途，以及人每天与它相处的感受。再看理解与尊重：易懂、不喧宾夺主、诚实。产品的结构要帮助人理解用途；作为工具，要给人的活动留出空间；呈现出来的能力，也要与真实能力相符。最后把时间拉长：经久耐用、细致、环保，以及尽可能少的设计。不只看第一次使用，还关心每个细节和长期影响。这三组是今天的讲述方式，不是 Rams 原本的分类。刚才的计算器提供了理解功能组织的一个入口，不能凭一张照片证明十项原则都做到了。第一章可以带走两个观察视角：Norman 帮我们理解人怎样使用产品，Rams 帮我们更完整地判断产品品质。下一章走进 UI 与 UX，看看这些思考怎样进入数字产品的设计。最后，我想从十项原则中单独留下一句话。

来源：Dieter Rams, Ten principles for good design, Vitsœ：https://www.vitsoe.com/us/about/good-design 。原则释义为中文概述；三组为本讲教学组织。

## 15 战略层：明确用户需求与产品目标

原书把战略层建立在两个问题上：我们希望通过产品得到什么，用户希望通过产品得到什么。前者是产品目标，后者是用户需求。产品目标可以包含业务目标、品牌身份，以及怎样衡量目标是否达成；用户需求则需要通过了解使用者来确认。书中进一步讨论用户细分、可用性与用户研究，以及人物角色。这里先抓住这两个出发点：团队的目标和使用者的需要都要有依据，它们共同影响后面的设计决定。左边从使用者看，右边从产品看，这两面需要放在一起考虑。接下来，范围层会把这些目标与需求转成要提供的具体功能和内容。

## 16 范围层：功能规格与内容需求

战略层明确为什么做，范围层进一步明确要做什么。按照原书的区分，功能一侧通过功能规格描述产品应当提供的功能；信息一侧通过内容需求说明需要提供哪些内容，以及这些内容有哪些要求。实际产品通常要同时考虑这两面。书中强调，把范围明确下来，也是在说明哪些事情暂时不做，使大家对正在建设的产品有共同认识。不同需求发生冲突时，还需要依据战略层的目标确定优先级。因此这里的功能规格和内容需求，都应当能追溯到用户需求与产品目标。接下来进入结构层，讨论功能怎样运作、内容怎样组织。

## 17 结构层：交互设计与信息架构

范围确定了要提供的功能与内容，结构层决定它们怎样组织和运作。原书在功能一侧讨论交互设计，也就是怎样回应使用者的行为。这里涉及人怎样理解系统的概念模型，以及发生错误时系统怎样帮助人继续。信息一侧讨论信息架构，关注内容怎样组织、怎样分类，以及组织原则、语言和元数据怎样帮助理解。左边的行为路径与右边的信息层级，是这两个方向的教学示意。它们都在处理整体关系，而下一层的框架，会进一步考虑人实际接触到的控件、导航与信息呈现。

## 18 框架层：界面设计、导航设计与信息设计

框架层在原书中包含三个紧密关联的部分。先看右边的关系：对于功能型产品，界面设计决定人通过哪些控件接触和操作功能；对于信息型产品，导航设计让人能够在信息结构中移动。信息设计同时支持两者，负责把信息表达得清楚、容易理解。所以它们虽然可以分别讨论，在实际界面里却需要共同工作。原书也提醒，导航方面的问题可能来自信息表达不清，界面问题也可能与信息设计有关，需要分清问题再处理。左边使用书中第 128 页的线框图例。它把导航、内容和操作控件放到同一页面，展示各部分怎样组合。线框图在这里记录框架层的设计决定，并为后续视觉设计和实现提供依据。框架层的工作因此包含控件、导航和信息表达的安排；接下来表现层会进一步处理人最终感知到的体验。

## 19 表现层：用视觉表达信息的主次

原书把表现层的核心称为感知设计，讨论产品怎样通过感官被体验，涉及视觉，也包括触觉与听觉等。结合屏幕界面，书中接着讨论视线怎样移动、对比与一致性、配色和排版，以及设计稿与风格指南。这里用视觉表达作一个局部说明。前面已经决定了提供哪些信息、怎样组织和安排，这一层进一步处理人最终怎样感知它们。这里用一个大家熟悉的天气界面举例，是为这节课做的示意，不是某个产品的实际截图。两边的内容与位置完全相同：城市、当前温度、天气、体感温度和最高最低温。大家看一眼，哪边更容易先读到当前天气？左边所有文字的大小、颜色和粗细都接近，读者需要自己逐项辨认。右边通过字号和明暗对比，把当前温度放到第一阅读层级；天气图形帮助辨认状态，体感和最高最低温作为补充信息。这里没有增加功能，也没有重新安排内容，改变的是信息的视觉表达。强调什么，应该由使用目的决定，而不是哪个地方方便加颜色就强调哪里。《用户体验要素》在表现层讨论对比、一致性、配色和排版，也提醒我们关注视线如何移动。表现层还包含其他感官的设计，这里以视觉为主。从表现层继续往下看，我们先沿用天气信息，观察间距怎样表达分组；再看操作目标怎样被指向。

来源：Jesse James Garrett《用户体验要素：以用户为中心的产品设计》第 2 版，依据用户提供的中文版 PDF；页码采用书内印刷页码，PDF 页序另列。中文讲述为本讲释义。 第 2 章 p.30；第 7 章 pp.134–149：感知设计；视觉、视线、对比与一致性、配色与排版、设计稿与风格指南。天气界面为本讲教学示意，不是原书案例。

## 21 Fitts 定律：距离与宽度影响指向操作

## 28 什么是设计系统（Design System）？

前面我们用 Atomic Design 理解了部件与整体：页面中的问题，也可能要回到组件和模板修改。如果这些设计需要在不同页面反复使用，就需要一套共同依据，这就是设计系统要解决的问题。什么是设计系统？这里采用 Nielsen Norman Group《Design Systems 101》的定义，意译为：设计系统是一套标准，通过可复用的组件与模式，支持规模化设计。可以把规模化理解为，让设计能够在多个界面中持续复用。看左边，原则与规范说明颜色、字体、间距和行为怎样表达；组件与用法把这些约定变成可以采用的资源、示例和代码。右边的不同页面使用它们，形成一致的表达。左侧底部还保留了持续维护：组件、规范与文档需要保持有效。这一点参考 Brad Frost《Atomic Design》第五章，对系统长期维护的讨论。图是本讲对关系的概括，具体范围会随产品和团队不同。 这里也区分三个概念：样式指南记录视觉与表达规范，组件库提供可复用部件，设计系统还连接使用规则、文档与维护。它们是相互配合的部分。下面看 Apple 与 Microsoft 的具体规范怎样指导界面决定。

## 34 人定目标与取舍，Agent 执行并返回结果

先看协作关系。人说明要解决什么问题、有哪些约束，并在看到结果后判断保留什么、修改什么。Agent 则可以读取设计资料、制作界面、调用浏览器或其他工具检查结果，再继续修改。它和只返回一段文字的聊天不同，能够通过工具把工作往前推进。人的反馈也会进入下一轮。能读取哪些资料、执行哪些操作，取决于工具和配置。带着这个关系，再看工具的区别：我们要继续编辑的是设计图层、可交互原型，还是现有代码？

来源：原理依据：Anthropic, Building effective agents，https://www.anthropic.com/research/building-effective-agents 。协作观察：Designer Fund 对 Anthropic 团队的访谈，https://designerfund.cc/blog/ai-design-anthropic 。人机协作回路为本讲归纳，非官方流程图。

## 35 选择工具，先看要继续编辑什么

先按工作对象认识工具。想继续在画布里调整图层，可以看 Figma 的 AI 能力；想尽快体验交互，可以看 Figma Make、Lovable；已经有代码工程，希望直接修改和运行，可以使用 Claude Code 这样的编程 Agent。这些能力会交叉，不是互斥分类。工具选择取决于下一步要怎样使用和修改结果。选好工具，还需要回答一个问题：它依据什么来做设计？这就进入第二块。

## 36 给 Agent 设计依据：Skills 与 DESIGN.md

Design Skill 把工作步骤、判断依据和参考资源组织起来，供 Agent 在相关任务中使用。例如 Anthropic 的 frontend-design 指导它理解受众、选择视觉方向；Impeccable 还提供评审、布局调整和细节打磨等操作。DESIGN.md 则常用来记录一个项目的设计约定：页面服务谁，信息怎样组织，哪些规范和组件应当沿用。两者可以重叠，Skill 也可以携带项目规范；DESIGN.md 并没有统一格式，文件存在也不代表工具已经读取。实际使用时，要把这些依据交到 Agent 手里。接下来分别看：一份 Skill 怎样帮助完成具体作品，一份设计指导怎样影响多个页面。

## 40 把反馈标在界面上，让 Agent 知道改哪里

这张图来自 Matt Dailey 的个人实践。他先让 Agent 汇总不同界面和状态的截图，再查看具体问题。图中他圈出一组居中的信息，明确要求改成左对齐。这样的反馈同时指出位置、问题和修改方向，比只说“再好看一点”更容易执行。他还会结合交互检查和团队反馈继续调整。与上一页 Anthropic 的团队经验放在一起看，AI 可以展开和实现，人则通过实际结果作判断，把反馈带回下一轮。第三章希望大家带走的，就是这种可见的协作过程，以及让它更稳定的工具和设计依据。

## 41 回到今天的三个问题

回到三个问题。好设计从人的需要出发，让产品容易理解、容易使用，也重视长期品质。做产品设计，可以先看清目标和内容，再组织信息、交互与视觉，用部件和设计系统复用共同决定。AI 带来新的协作方式：人提供目标、依据和判断，Agent 帮助展开与实现，再通过实际体验和评审继续修改。希望大家在平时工作中，也能用今天这些视角观察界面、讨论方案。下面留下书籍与案例的原始链接。
